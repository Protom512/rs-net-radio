# Requirements Document

## Introduction
本リファクタリングプロジェクトは、長期間メンテナンスされていない録音アプリケーションの品質向上と技術的負債の解消を目的とする。Vlad Khononovの『Balancing Coupling in Software Design』に基づく結合度のバランス改善、Rustパッケージのアップデート、適切なエラーハンドリングの実装、非同期/同期処理の最適化、並列処理の改善、およびバッチ/ストリーミング録音機能の整理を行う。

## Requirements

### Requirement 1: バッチ録音機能

**Objective:** ユーザーとして、任意のタイミングでバッチ形式でラジオ番組をダウンロードしたい、録音の柔軟性を向上させるため。

**Dependencies:**
- Requirement 5: 並列処理とパフォーマンス（セマフォによる同時実行数制御に依存）
- Requirement 6: 非同期I/O処理（非同期HTTPクライアントによるダウンロードに依存）

#### Acceptance Criteria

1. **Event-driven**: When ユーザーがバッチ録音コマンドを実行した時、システムは指定された番組リストの並列ダウンロードを開始しなければならない

2. **State-driven**: While ダウンロード処理が実行中の状態において、システムは現在の進捗率（完了タスク数/全タスク数×100%）を標準出力にリアルタイムで表示しなければならない

3. **Unwanted Behavior**: If 特定の番組のダウンロードに失敗した場合、システムは失敗した番組名とエラーメッセージをログ(`error.log`)に記録し、リスト内の次の番組の処理を継続しなければならない

4. **Event-driven**: When バッチ録音が全タスク完了した時、システムは成功件数、失敗件数、合計処理時間のサマリーを標準出力に出力しなければならない

5. **Ubiquitous**: システムはバッチ録音の並列数、リトライ回数、接続タイムアウト（デフォルト30秒）を設定ファイル(`config.toml`)から読み込み、適用しなければならない

---

### Requirement 2: ストリーミング録音機能

**Objective:** ユーザーとして、cronを使用した定時録音機能を使用したい、信頼性の高い自動録音を実現するため。

**Dependencies:**
- Requirement 3: Hibikiラジオ対応（Hibikiサイトでの録音に依存）
- Requirement 4: エラーハンドリング（再接続リトライに依存）
- Requirement 6: 非同期I/O処理（TCP接続の非同期実行に依存）

#### Acceptance Criteria

1. **Event-driven**: When 設定ファイル(`cron.toml`)で定義されたスケジュールに従い録音時刻に到達した時、システムは対象のストリームURLへのTCP接続を開始しなければならない

2. **State-driven**: While ストリーミングデータを受信している間、システムはデータを4KBチャンク単位でディスクへ書き出し、メモリ使用量を512MB以下に維持しなければならない

3. **Unwanted Behavior**: If ストリーミング録音中にネットワークエラーが発生した場合、システムは接続失敗をログに記録し、指数バックオフ（初期1秒、最大60秒）で再接続を試みなければならない

4. **Event-driven**: When 録音が正常に完了した時、システムはメタデータ（番組名、録音開始日時、録音終了日時、ファイルサイズ、ビットレート）をJSONファイル(`metadata.json`)に保存しなければならない

5. **Unwanted Behavior**: If 再接続を5回試行して失敗した場合、システムは録音を中止し、終了コード1でプロセスを終了しなければならない

---

### Requirement 3: Hibikiラジオ対応

**Objective:** ユーザーとして、Hibikiラジオサイトの仕様変更に対応した録音機能を使用したい、安定した録音体験を維持するため。

**Dependencies:**
- Requirement 4: エラーハンドリング（HTTPエラー処理に依存）
- Requirement 6: 非同期I/O処理（非同期HTTPリクエストに依存）

#### Acceptance Criteria

1. **Event-driven**: When Hibikiラジオサイトへのアクセスを開始した時、システムはUser-Agentヘッダ（`Mozilla/5.0 ...`）とRefererヘッダを含めたHTTPリクエストを送信しなければならない

2. **Unwanted Behavior**: If HTTPステータスコード403または429を受信した場合、システムは「アクセス拒否: サイトの利用規約を確認してください」というメッセージを標準エラー出力に出力し、終了コード2で終了しなければならない

3. **Event-driven**: When HTML解析を実行した時、システムはストリーミングURLを抽出し、解析に失敗した場合は「HTML解析エラー: サイト構造が変更されている可能性があります」をログに記録しなければならない

4. **Unwanted Behavior**: If サイトのHTML構造が変更されストリーミングURLが見つからない場合、システムは「ストリーミングURLが見つかりません: サイト仕様が変更されている可能性があります」を標準エラー出力に出力し、終了コード3で終了しなければならない

5. **Ubiquitous**: システムはHTML解析ロジックを独立したモジュール(`hibiki_scraper.rs`)に実装し、単体テストで抽出結果を検証できなければならない

---

### Requirement 4: エラーハンドリング

**Objective:** システムとして、回復可能なエラーは適切に処理し、致命的なエラーは明確に報告したい、実行時の安全性とデバッグ効率を向上させるため。

#### Acceptance Criteria

1. **Event-driven**: When 実行時に回復可能なエラー（ネットワーク一時的エラー、ファイル書き込み一時的失敗など）が発生した時、システムは`Result<T, E>`型を介して呼び出し元にエラーを伝播しなければならない

2. **Unwanted Behavior**: If 致命的なエラー（設定ファイルの欠如、ディスク容量不足、権限エラー）が発生した場合、システムはパニックを発生させず、エラーコンテキストを付加したエラーメッセージを標準エラー出力に出力し、終了コード1で終了しなければならない

3. **Event-driven**: When ライブラリがエラーを返した時、システムはエラーの発生源（モジュール名、関数名）とエラー内容を`error.log`に記録しなければならない

4. **Ubiquitous**: システムは`unwrap()`または`expect()`を呼び出す箇所を0個にし、すべてのエラー処理を`?`演算子または`match`式で行わなければならない

5. **Unwanted Behavior**: If アプリケーションのメイン関数でエラーをキャッチできなかった場合、システムはエラーメッセージをスタックトレース付きで`error.log`に記録し、終了コード1で終了しなければならない

---

### Requirement 5: 並列処理とパフォーマンス

**Objective:** システムとして、複数の録音タスクを安全に並列実行したい、スケーラビリティとリソース効率を改善するため。

**Dependencies:**
- Requirement 6: 非同期I/O処理（非同期ランタイムでのタスク実行に依存）

#### Acceptance Criteria

1. **Event-driven**: When 複数の録音タスクを並列実行する時、システムはセマフォを使用して同時実行数を設定ファイル(`config.toml`の`max_parallel_jobs`、デフォルト3)に制限しなければならない

2. **State-driven**: While 並列タスクが実行中の状態において、システムはデータ競合を引き起こす可変共有状態を持たず、各タスクは独立したメモリ空間で動作しなければならない

3. **Event-driven**: When 並列タスクの結果を収集する時、システムは`JoinSet`を使用してタスク完了順に結果を処理し、全タスクの結果を集計しなければならない

4. **Unwanted Behavior**: If セマフォの許容量を超えた並列実行を試みた場合、システムは「同時実行数の上限に達しました: 待機しています」をログに記録し、許容量内に収まるまで待機しなければならない

5. **Ubiquitous**: システムは並列処理に関するコードに対し、`Send`と`Sync`トレイト境界をコンパイル時に検証し、スレッド安全性を保証しなければならない

---

### Requirement 6: 非同期I/O処理

**Objective:** システムとして、I/Oバウンドな処理を効率的に実行したい、リソース使用率を最適化するため。

#### Acceptance Criteria

1. **Event-driven**: When HTTPリクエストを開始した時、システムは非同期HTTPクライアント(`reqwest`)を使用してリクエストを実行しなければならない

2. **State-driven**: While 非同期I/O処理が実行中の状態において、システムは`tokio`ランタイムのワーカースレッドをブロッキング処理でブロックしてはならない

3. **Unwanted Behavior**: If CPUバウンドな処理（エンコード、暗号化など）を非同期コンテキストで実行する必要がある場合、システムは`spawn_blocking`を使用して専用スレッドプールで処理しなければならない

4. **Event-driven**: When タスク間でデータを共有する時、システムは`Arc<Mutex<T>>`の代わりにチャネル(`mpsc`)を使用したメッセージパッシングでデータを転送しなければならない

5. **Ubiquitous**: システムはTokioランタイム(`multi_thread` scheduler)を使用し、一貫した非同期処理モデルを適用しなければならない

---

### Requirement 7: パフォーマンス改善

**Objective:** システムのユーザーとして、アプリケーションが応答性を維持し、長時間かかる処理が他の操作をブロックしないようにしたい。これにより、スムーズなユーザーエクスペリエンスが実現される。

**Dependencies:**
- Requirement 5: 並列処理とパフォーマンス（並列処理によるCPU効率化に依存）
- Requirement 6: 非同期I/O処理（非同期タスク実行に依存）

#### Acceptance Criteria

1. **State-driven**: While 長時間実行される録音処理がアクティブな状態において、アプリケーションのメインスレッドはブロックされず、ユーザー入力に応答し続けなければならない

2. **Event-driven**: When FFmpegプロセス（録音データのエンコード処理）のようなブロッキングI/O操作が開始された時、システムはそれを別のスレッドまたは非同期タスクで実行しなければならない

3. **Ubiquitous**: システムは適用可能な場合、並列処理によってCPUコアを効率的に利用しなければならない

---

### Requirement 8: コード構造のリファクタリング

**Objective:** 開発者として、責務が明確に分離され、テストが容易なコードベースで作業したい。これにより、機能追加やバグ修正が迅速かつ安全に行えるようになる。

**Dependencies:**
- Requirement 9: テスト容易性の向上（テスト可能な構造に依存）

#### Acceptance Criteria

1. **Ubiquitous**: システムのアーキテクチャは、`.kiro/steering/rust-senior.md`のProject Structure Guidelinesに従い、`domain`、`infra`、`api` のような明確なレイヤーに分離されなければならない

2. **Optional Feature**: Where ビジネスロジックが実装されている箇所、それは外部のフレームワークやライブラリ（例：データベース、Webサーバー）から独立していなければならない

3. **Ubiquitous**: システムはデータアクセスにリポジトリ抽象化を提供し、ビジネスロジックに影響を与えることなく基盤となるストレージメカニズムを交換可能にしなければならない

4. **Ubiquitous**: システムはアプリケーション固有のビジネスルールフローを調整する明確な「ユースケース」または「サービス」を定義しなければならない

---

### Requirement 9: テスト容易性の向上

**Objective:** 開発者として、各コンポーネントを独立してテストできる能力が欲しい。これにより、コードの品質と信頼性が向上する。

**Dependencies:**
- Requirement 8: コード構造のリファクタリング（モジュール分離に依存）

#### Acceptance Criteria

1. **Ubiquitous**: システムのビジネスロジック（ドメイン層）は、データベースや外部APIの実行を必要とせずに、単体テストでテスト可能でなければならない

2. **Optional Feature**: Where 依存関係が注入される箇所（例：リポジトリ、外部サービス）、それらはテストでモック実装を可能にするため、トレイト（インターフェース）に基づいていなければならない

3. **Ubiquitous**: プロジェクトはバッチ録音、ストリーミング録音、Hibikiラジオ対応の主要機能をカバーする単体テストと統合テストの包括的なスイートを含まなければならない

---

### Requirement 10: 堅牢性と保守性の向上

**Objective:** 運用者として、エラーが適切に処理され、システムの状況が明確にログに記録される安定したシステムが欲しい。これにより、問題の診断と解決が容易になる。

**Dependencies:**
- Requirement 4: エラーハンドリング（エラー伝播メカニズムに依存）

#### Acceptance Criteria

1. **Unwanted Behavior**: If バックグラウンド処理中（例：録音）にエラーが発生した場合、システムは十分なコンテキストと共にエラーをログに記録し、アプリケーション全体をクラッシュさせてはならない

2. **Ubiquitous**: システムはすべてのアプリケーションイベントに対して構造化ロギング（`tracing`クレートを使用）を使用しなければならない

3. **Ubiquitous**: システムは`.kiro/steering/rust-senior.md`に定義されたエラー処理戦略に従い、ライブラリには`thiserror`を、アプリケーションレベルのエラー伝播には`anyhow`を使用して型付けられたエラーを実装しなければならない

---

### Requirement 11: バックワード互換性

**Objective:** 既存ユーザーとして、リファクタリング後も既存の設定ファイルと録音データがそのまま使用できることを期待する。

**Dependencies:**
- Requirement 4: エラーハンドリング（設定ファイル読み込みエラーに依存）

#### Acceptance Criteria

1. **Ubiquitous**: システムは既存の`config.toml`形式を読み込み、リファクタリング後の新形式に変換して使用しなければならない

2. **Event-driven**: When 既存の録音データディレクトリを検出した時、システムは新形式への移行ツールを提供し、ユーザーの確認を得た上でデータ移行を実行しなければならない

3. **Unwanted Behavior**: If 既存の設定ファイルに互換性のない項目が含まれる場合、システムは警告メッセージを表示し、デフォルト値を使用して処理を継続しなければならない

---

## Development Constraints (開発時の制約)

本セクションは開発プロセスにおける制約条件を記述します。これらはシステムの実行時振る舞いではなく、開発時の品質基準です。

### Architecture Constraints

1. **結合度の制約**: システムはVlad Khononovの『Balancing Coupling in Software Design』に基づき、以下の結合度ルールに従わなければならない
   - 制御結合（Control Coupling）を禁止: 制御フラグや列挙型による振る舞いの制御を使用しない
   - データ結合（Data Coupling）を優先: プリミティブ型またはデータ構造のみを渡す
   - モジュール間の依存はトレイト境界を通じて抽象化する

2. **モジュール構造**: システムはドメイン層、インフラ層、API層を分離し、上位モジュールが下位モジュールに依存しない構造を維持しなければならない

3. **レイヤー分離**: `domain`層は外部フレームワークやライブラリから独立し、`infra`層は技術的実装をカプセル化し、`api`層は外部インターフェースを提供しなければならない

4. **リポジトリパターン**: データアクセスはリポジトリトレイトを通じて抽象化され、実装を交換可能にしなければならない

5. **ユースケース/サービス層**: ビジネスルールフローを調整する明確なユースケースまたはサービスを定義しなければならない

### Code Quality Constraints

1. **エラーハンドリング**: ライブラリレイヤーでは`thiserror`で型安全なエラーを定義し、アプリケーションレイヤーでは`anyhow`でコンテキスト情報を付加しなければならない

2. **型安全性**: 状態遷移にはTypestateパターン、プリミティブ型のラップにはNewtypeパターンを使用しなければならない

3. **コンパイル検証**: `unwrap()`/`expect()`の使用を禁止し、全てのエラー処理を`?`演算子または`match`式で行わなければならない

4. **ファイルサイズ**: 1ファイルの行数を300行以下に保ちなければならない

5. **依存性注入**: 依存関係はトレイト（インターフェース）を通じて注入し、テスト時にモック実装を可能にしなければならない

6. **構造化ロギング**: すべてのアプリケーションイベントは`tracing`クレートを使用して構造化ログとして記録しなければならない

### Dependency Management Constraints

1. **パッケージ更新**: セキュリティ脆弱性を持つパッケージは脆弱性が解消されたバージョンに更新しなければならない

2. **破壊的変更**: 依存パッケージに破壊的変更が含まれる場合、移行ガイドに従って適切に対応しなければならない

3. **標準準拠**: 新しいパッケージを追加する場合、Rustコミュニティのde facto standardに準拠した選択をしなければならない

### Testing Constraints

1. **単体テスト**: ドメイン層のビジネスロジックは、データベースや外部APIの実行を必要とせずに単体テストでテスト可能でなければならない

2. **テストカバレッジ**: プロジェクトはアプリケーションのクリティカルパスをカバーする単体テストと統合テストの包括的なスイートを含まなければならない

3. **モック可能性**: 依存関係はトレイトベースで実装され、テスト時にモック実装を可能にしなければならない

### Performance Constraints

1. **応答性**: 長時間実行される処理中、メインスレッドはブロックされず、ユーザー入力に応答し続けなければならない

2. **非同期処理**: ブロッキングI/O操作（FFmpegプロセスなど）は、別のスレッドまたは非同期タスクで実行されなければならない

3. **CPU効率**: 適用可能な場合、並列処理によってCPUコアを効率的に利用しなければならない

### Reliability Constraints

1. **エラー分離**: バックグラウンド処理中のエラーは、アプリケーション全体をクラッシュさせてはならない

2. **エラーコンテキスト**: エラーが発生した場合、十分なコンテキストと共にログに記録しなければならない

3. **ログ保存**: すべてのエラーイベントは`error.log`に永続化されなければならない
